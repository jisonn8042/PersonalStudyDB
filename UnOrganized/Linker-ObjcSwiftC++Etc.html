(그래서 Shared Library라고도 부릅니다.) 3. 유지보수와 업데이트 (Maintenance) 개발자가 버그를 수정했을 때 어떻게 배포하느냐의 차이입니다. 정적 라이브러리: 라이브러리에 버그가 있으면, 그 라이브러리를 사용한 모든 앱을 다시 빌드(Re-compile)해서 새로 설치해야 합니다. 앱 개발자 입장에서는 매우 번거롭습니다. 동적 라이브러리: 라이브러리 파일(.dll, .dylib) 하나만 쓱 교체하면 됩니다. 앱을 다시 설치할 필요 없이, 다음에 앱이 켜질 때 수정된 라이브러리를 불러오게 됩니다. ClassA가 MethodB를 부르면 MethodB를 가져옵니다. (꼬리에 꼬리를 무는 방식) 삭제(Strip): 이 연결 고리(Dependency Graph)에 걸리지 않는, 외딴섬 같은 코드들은 **"도달 불가능(Unreachable)"**하다고 판단하여 삭제합니다. 3. 왜 카테고리만 '오판'하는가? MyClass 파일 가져와!"" 판단 결과 포함 (Link) 카테고리 메서드 호출 [obj myCategoryMethod]; 음... obj에게 메시지를 보내네? 근데 이건 실행해봐야 아는 거잖아(Dynamic Dispatch). 지금 내 눈엔 myCategoryMethod가 어느 파일에 있는지 안 보여." 판단 결과 제외 (Strip) 일반 클래스: 코드상에 MyClass라는 이름이 명시적으로 나오므로 링커가 "필요함" 도장을 찍습니다. 카테고리: Objective-C는 메서드를 호출할 때, 실행 중에 우체부(objc_msgSend)가 편지를 배달하는 방식입니다. 링커(건축가)는 건물을 지을 때(빌드 타임) 우체부가 나중에 어디로 갈지 알 수가 없습니다. 그래서 링커는 **"이 카테고리 파일은 아무도 직접 가리키고 있지 않네? 연결 끊긴 섬이구나. 버려!"**라고 판단해버리는 것입니다. 4. 요약 링커의 판단 기준 변화를 정리하면 다음과 같습니다. 과거: "파일이 있으면 포함한다." (단순함, 용량 큼, 안전함) 현재: "참조의 연결 고리가 확인된 것만 포함한다." (복잡함, 용량 작음, 효율적) 부작용: Objective-C 카테고리는 **'연결 고리가 런타임(실행 중)에 형성'**되는데, 정적 링커는 '빌드 타임(건축 중)'에 판단하므로 이를 "쓰지 않는 코드"로 착각하고 버리게 됨. 이러한 '정적 분석의 한계' 때문에 개발자가 -ObjC 옵션을 통해 **"판단하지 말고 그냥 다 넣어!"**라고 링커의 눈을 가리는 강제 명령을 내려야 하는 것입니다. 링커는 크게 **① 작동하는 시점(방식)**과 **② 실제로 구현된 도구(프로그램)**에 따라 종류가 나뉩니다. 앞서 이야기 나눈 'Objective-C 카테고리 파일 누락 문제'를 더 잘 이해하기 위해서는 작동 시점에 따른 분류를 아는 것이 가장 중요합니다. 1. 작동 시점에 따른 분류 (가장 중요)링커가 언제 일을 하느냐에 따라 정적 링커와 동적 링커로 나뉩니다. ① 정적 링커 (Static Linker)언제: 개발자가 앱을 빌드(Build/Compile)할 때 작동합니다. 하는 일: 작성한 소스 코드(.o)와 라이브러리(.a)를 모아서 하나의 완성된 실행 파일로 꽁꽁 묶어버립니다. 특징:필요한 코드를 실행 파일 안에 다 집어넣기 때문에 파일 크기가 커집니다.앞서 말한 -ObjC 문제가 발생하는 곳이 바로 여기입니다. 정적 링커가 빌드 과정에서 "이 카테고리 파일 안 쓰는 것 같으니 뺄게!"라고 판단해버리는 것이죠. ② 동적 링커 (Dynamic Linker)언제: 사용자가 앱을 실행(Run)할 때 작동합니다. (런타임) 하는 일: 실행 파일이 켜질 때, 외부에 있는 공유 라이브러리(.dylib, .dll, .so)를 찾아서 연결해 줍니다. 특징:iOS/macOS에서는 **dyld**라고 부릅니다.여러 앱이 공통으로 쓰는 기능(예: UIKit, Foundation 등 시스템 프레임워크)은 앱 안에 넣지 않고, 이 동적 링커가 실행될 때 OS에서 빌려옵니다. 2. 구현 도구(프로그램)에 따른 분류실제로 개발 환경(IDE)에서 돌아가는 링커 프로그램의 이름들도 다양합니다. 운영체제나 컴파일러에 따라 다른 링커를 씁니다. 이름 설명 주요 사용 환경 ld 가장 전통적이고 표준적인 유닉스 계열 링커입니다. 리눅스, 구형 시스템 lldLLVM 프로젝트의 링커입니다. 기존 ld보다 속도가 훨씬 빠릅니다.(gold보다 속도가 4배 빠름, 현역) 현재의 iOS/macOS (Xcode), 안드로이드, Chrome gold 구글이 만든 리눅스용 ELF 링커입니다. 속도 최적화를 위해 만들어졌습니다.(현재 지원 중단) 리눅스 서버 개발 등 link.exe 마이크로소프트 비주얼 스튜디오에 포함된 링커입니다. Windows 개발요약: 작성하시는 글과의 연결지금 작성 중이신 '링커의 동작'과 관련해서는 다음 두 가지를 구분하시면 내용이 훨씬 풍성해질 것입니다. 빌드 단계 (Static Linking): 개발자가 Xcode에서 'Build' 버튼을 눌렀을 때, ld 또는 lld라는 정적 링커가 돌아가며 불필요한 코드를 제거(Stripping)하다가 카테고리 파일을 실수로 빼먹는 상황. (해결책: -ObjC 플래그)실행 단계 (Dynamic Linking): 앱이 아이폰에서 켜질 때, **동적 링커(dyld)**가 시스템 라이브러리들을 연결해주며 앱을 구동시키는 과정.
