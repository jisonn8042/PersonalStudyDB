Ⅰ. SSH設定

1. SSHキー生成

GitHubと連携するためのSSHキーを生成します。


生成

# -f を活用し任意の名前でキーを生成します。
ssh-keygen -t ed25519 -C "[GitHub用メールアドレス]" -f ~/.ssh/[任意の名前]

#入力例
ssh-keygen -t ed25519 -C "example@example.com" -f ~/.ssh/personal_github

確認

#コマンドを入力時任意の名前になっているファイルの有無を確認します。
ls -al ~/.ssh

2. キーチェイン設定

macを再起動してもパスワードを毎回入力するのを防ぐためにキーチェインに登録します。


#キーチェインに登録
ssh-add --apple-use-keychain ~/.ssh/[任意の名前]

#入力例
ssh-add --apple-use-keychain ~/.ssh/personal_github

3. GitHubにSSHキーを登録

GitHubにSSHキーを登録します。


#GitHubにSSHキーを登録
cat ~/.ssh/[任意の名前].pub | pbcopy

#入力例
cat ~/.ssh/personal_github.pub | pbcopy

4. ~/.ssh/config生成・設定

~/.ssh/configファイルを生成・設定します。

設定



#~/.ssh/configファイルを設定
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work  # 회사에서 발급받거나 생성한 업무용 키
    UseKeychain yes
    AddKeysToAgent yes

#入力例
# ----------------------------
# 1. 会社用 アカウント (基本値として設定する場合が多い)
# ----------------------------
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work  # 회사에서 발급받거나 생성한 업무용 키
    UseKeychain yes
    AddKeysToAgent yes

# ----------------------------
# 2. 個人用 アカウント (Alias(別名)を使用)
# ----------------------------
Host github-personal             # 呼び出す別名
    HostName github.com          
    User git
    IdentityFile ~/.ssh/personal_github  #作った個人用SSHキー
    IdentitiesOnly yes           # エージェントが他のキーを無視する
    UseKeychain yes
    AddKeysToAgent yes

5. ローカルGit設定

ローカルGit設定を行います。

設定


#ローカルGit設定
git config --global user.name "[名前]"
git config --global user.email "[メールアドレス]"

#入力例
git config --global user.name "Jisung Park"
git config --global user.email "jisungpark8024@gmail.com"

確認


#Git設定確認
git config --global user.name
git config --global user.email

SSHとは


git --global user.name git --global user.email git config user.name git config user.email mac에서 github와 ssh연동시 주의 사항 mac의 ssh-agent는 2. 문제 발생 시나리오 (설정이 없을 때) 사용자가 github-personal (계정: jisonn8042)에 접속하려고 합니다. 접속 시도: 사용자가 git push를 합니다. 에이전트의 개입: SSH 에이전트가 나섭니다. "주인님, 제가 열쇠 꾸러미를 가지고 있어요. 제일 먼저 등록된 **A열쇠(JisungPark8024용)**부터 찔러볼게요." GitHub의 반응 (여기가 중요!): GitHub 입장에서는 A열쇠도 당신이 등록한 유효한 열쇠입니다. GitHub: "어? A열쇠네? 인증 성공! 너는 지금부터 JisungPark8024야." (로그인 성공) 권한 확인 실패: 로그인이 된 상태(JisungPark8024)에서 jisonn8042/PersonalStudyDB 저장소에 쓰기(Push)를 시도합니다. GitHub: "잠깐, 너는 JisungPark8024잖아? 저 저장소는 jisonn8042 꺼야. 권한 없어(Permission Denied)." 결과: 에러 발생. (에이전트가 B열쇠(jisonn8042용)를 꺼내보기도 전에 A열쇠에서 덜컥 로그인이 되어버려서 망한 케이스입니다.) 3. 해결책: IdentitiesOnly yes의 역할 이 옵션은 SSH 클라이언트에게 다음과 같이 명령하는 것입니다. "야, 에이전트가 옆에서 무슨 열쇠를 들이밀든 싹 무시해. 오직 내가 IdentityFile로 지정한 이 파일(B열쇠) 딱 하나만 써서 접속해." 이렇게 하면: 접속 시도 시, 에이전트가 A열쇠를 들이밀려고 해도 무시합니다. 설정파일에 적힌 **B열쇠(jisonn8042용)**만 서버에 제출합니다. GitHub: "어? B열쇠네? 너는 jisonn8042구나." 저장소 접근: "본인 저장소 맞네. 통과!" 요약 GitHub는 하나의 도메인(github.com)에서 여러 계정을 처리하기 때문에, "아무 열쇠나 일단 맞으면 로그인시켜버리는" 특성이 있습니다. 그래서 **"내가 지정한 이 열쇠가 아니면 시도조차 하지 마"**라고 명시해주는 IdentitiesOnly yes가 필수적인 것입니다. 좋은 질문입니다. 기술적으로 깊이 들어가면 SSH 프로토콜의 설계 철학과 GitHub라는 서비스의 특수성이 맞물려 있는 흥미로운 문제입니다. 하나씩 명쾌하게 풀어드릴게요. 1. 왜 Cursor에서는 문제가 없었을까? (Cursor vs Terminal) Cursor(혹은 VS Code)와 터미널(Antigravity)은 git 명령어를 실행하는 환경이 미묘하게 다릅니다. Antigravity (터미널): 운영체제(macOS)의 **표준 ssh-agent**와 가장 직접적으로 소통합니다. 현재 당신의 터미널 환경변수(SSH_AUTH_SOCK)가 가리키는 에이전트는 JisungPark8024 키를 가장 "우선순위가 높은 키"로 들고 있었을 확률이 100%입니다. 터미널은 "에이전트가 주는 게 정답이겠지" 하고 순진하게 그 키를 썼다가 사단이 난 것입니다. Cursor (GUI 에디터): Cursor는 자체적인 Git 통합 기능을 내장하고 있습니다. Cursor가 git을 실행할 때는 시스템의 ssh-agent에 전적으로 의존하기보다, **자체적인 자격 증명 관리자(Credential Helper)**를 먼저 타거나, 혹은 git config에 설정된 유저 정보를 보고 더 똑똑하게 판단했을 가능성이 높습니다. 즉, Cursor는 "무식하게 에이전트가 주는 첫 번째 키"를 쓴 게 아니라, "이 프로젝트는 jisonn8042 꺼니까 이 키를 써야지"라고 내부적으로 교통정리를 해줬을 수 있습니다. 2. 왜 IdentitiesOnly yes가 기본값이 아닐까? "왜 이렇게 귀찮게 설정을 따로 해야 해? 그냥 기본으로 켜두면 안 돼?"라는 의문은 정말 타당합니다. 하지만 SSH 개발자들 입장에서는 **"편의성"**이 더 중요했습니다. 이유 A: "설정 파일 없이도 동작해야 한다" (Zero Configuration) SSH의 기본 철학은 **"사용자가 아무 설정도 안 해도, 키만 있으면 접속돼야 한다"**입니다. 대부분의 개발자는 서버 하나에 키 하나만 씁니다. 만약 IdentitiesOnly yes가 기본값이라면, 모든 사람은 SSH 접속을 할 때마다: 반드시 설정 파일을 만들고, IdentityFile 경로를 일일이 지정해줘야만 접속이 됩니다. 이는 범용성 측면에서 너무 불편한 일입니다. 이유 B: 이 문제는 "GitHub의 특수성" 때문입니다 사실 이 문제는 SSH의 잘못이라기보다, 우리가 SSH를 "한 집(GitHub.com)에 사는 두 명의 다른 사람"에게 접속하려 해서 생긴 문제입니다. 일반적인 SSH 사용: 서버A.com 접속 -> A키 사용 서버B.com 접속 -> B키 사용 서로 주소가 다르므로 키가 섞일 일이 없습니다. 에이전트가 아무리 키를 많이 들고 있어도 상관없죠. GitHub 상황: github.com (회사 계정) -> A키 필요 github.com (개인 계정) -> B키 필요 주소(Host)가 똑같습니다! SSH 입장에서는 "어? 같은 집(github.com)에 가는데 왜 키를 까다롭게 골라? 그냥 문 열리는 키 아무거로나 들어가면 되잖아?" 라고 생각하는 겁니다. 그래서 기본 설정(Agent Forwarding)이 "가진 키 다 찔러보기"로 되어 있는 것이죠. 요약하자면 Cursor는 똑똑해서 (혹은 독자적인 방식으로) 당신이 의도한 키를 잘 골라 잡았거나, 에이전트의 간섭을 덜 받았습니다. IdentitiesOnly yes가 기본이 아닌 이유는, 일반적인 상황(서로 다른 서버에 접속)에서는 에이전트가 알아서 키를 찾아주는 게 훨씬 편하기 때문입니다. 우리는 지금 **"같은 주소(GitHub)에 다른 신분(계정)"**으로 접속하려는 특수한(Edge Case) 상황이라서, 수동으로 "엄격 모드"를 켜줘야 하는 것입니다. 이제 .ssh/config에 IdentitiesOnly yes를 추가하시고 사용하시면, 터미널에서도 Cursor처럼 깔끔하게 동작할 것입니다. 바로 적용해 보시겠어요? 한 서비스에 여러 ssh키를 사용할 때 아하 그렇구나 특정 alias로 설정되어 있어서 IdentitiesOnly yes를 설정해도 SourceTree의 통신에는 영향을 미치지 않는구나 이러한 측면에서 봤을때 같은 서비스에 여러 계정을 사용하려 한다면 alias를 설정하는게 좋겠다 ssh로 통신시 정해진 프로토콜이나 규약이 있어? 앞은 연결할 서비스 ＠뒤는 사용할 ssh키의 Host이름 이라던지 네, 정확히 보셨습니다! **"같은 서비스에 여러 계정을 쓸 때는 Alias(별칭)를 쓴다"**는 것이 이 문제의 정석적인 해결법입니다. 궁금해하신 **SSH 통신 주소의 규칙(앞@뒤)**에 대해 아주 명확하게 정리해 드릴게요. 우리가 흔히 쓰는 이메일 주소와 비슷해 보이지만, 의미는 전혀 다릅니다. 1. SSH 접속 주소의 기본 공식 SSH 명령어의 기본 문법은 다음과 같습니다. Bash ssh [유저이름]@[호스트주소] [유저이름] (앞): 원격 컴퓨터(서버)에 로그인할 운영체제 계정 이름 [호스트주소] (뒤): 원격 컴퓨터의 IP 주소 또는 도메인 (혹은 우리가 만든 Alias) 2. git@github-personal의 해부 질문하신 내용인 "앞은 연결할 서비스, 뒤는 SSH 키의 Host 이름"이 맞는지, 실제 git@github-personal을 예로 들어 뜯어보겠습니다. ① 앞부분 (git) : 서비스 이름이 아니라 "문지기 이름" 오해: "GitHub니까 git이라고 쓰는 건가?" 진실: GitHub 서버(리눅스)에 존재하는 실제 사용자 계정 이름이 git입니다. GitHub는 전 세계 모든 사용자를 git이라는 단 하나의 리눅스 계정으로 접속시킵니다. jisungpark@github.com (X) -> 이렇게 접속하지 않습니다. git@github.com (O) -> 무조건 이걸로 통일입니다. 대신, **"누가 접속했냐"**는 오직 **SSH Key(열쇠)**로만 구별합니다. ② 뒷부분 (github-personal) : 이게 바로 우리가 만든 "지름길(Alias)" 원래는 도메인(github.com)을 써야 합니다. 하지만 우리가 .ssh/config에 Host github-personal이라고 이름을 붙여놨죠? SSH는 이 뒷부분을 보고 설정 파일을 뒤집니다. "어? 주소가 github-personal이네? 설정 파일에 이런 이름이 있나? 아, 여기 있네! 실제 주소(HostName)는 github.com으로 바꾸고, 열쇠(IdentityFile)는 id_ed25519를 챙겨가야지." 3. 그림으로 요약 (변환 과정) 사용자가 터미널에 입력한 명령어: git clone git@github-personal:username/repo.git SSH가 내부적으로 변환해서 실행하는 실제 모습: Bash # [유저] [실제주소(HostName)] [지정된 열쇠] ssh git @ github.com -i ~/.ssh/id_ed25519 4. 결론 질문하신 내용에 맞춰 정리하면 다음과 같습니다. @ 앞부분 (git): 연결할 서비스의 이름이 아니라, **"서버의 공통 계정 이름"**입니다. (GitHub, GitLab, Bitbucket 모두 보안상 git이라는 계정 하나만 열어둡니다.) @ 뒷부분 (github-personal): 말씀하신 대로 **"우리가 설정 파일(config)에 정의한 Host의 이름(Alias)"**이 맞습니다. 이제 구조가 완전히 눈에 들어오시죠? 이 원리만 알면 나중에 회사 계정, 개인 계정, 토이 프로젝트 계정 등 10개가 생겨도 config 파일에 Alias만 추가해서 완벽하게 관리할 수 있습니다!
